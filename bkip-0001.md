## Abstract

Bitcoin Knots replaces SHA256d proof of work with a layered construction
over BLAKE2b, carried in a new 164-byte block header, and introduces a
new opt-in signature hash. Both activate together, at a fixed height per
network.

This document specifies the header layout, the proof-of-work hash, the
signature hash, the activation rules, and the RPC surface, in enough
detail to implement against without reading the C++.

**The fork is two changes, not one.** A reader who takes it for a
proof-of-work change alone will produce a node that syncs and a wallet
whose signatures are wrong.

## 1. Terminology

**BTK** is the consensus branch created by this change, as distinct from
BTC. A **v1 header** is the historical 80-byte header hashed with
SHA256d. A **v2 header** is the 164-byte header specified here.

## 2. Distinguishing the two formats

**Bit 31 of `nVersion` on the wire flags the format.** Set means v2.

That bit is not part of the version number. Knots stores the format
separately and masks the flag off the stored `nVersion`, re-applying it
only when serializing:

```
VERSION_HEADER_V2_FLAG = 0x8000_0000

on deserialize:  m_header_v2 = v & VERSION_HEADER_V2_FLAG
                 nVersion    = v & ~VERSION_HEADER_V2_FLAG

on serialize:    v = (m_header_v2 ? VERSION_HEADER_V2_FLAG : 0)
                     | (nVersion & ~VERSION_HEADER_V2_FLAG)
```

**This is not a backwards-compatible reading of existing bytes.** Bit 31
was a usable version bit; an implementation that adds v2 support changes
what a header with that bit set means. Historical blocks do not set it,
but software that must read both chains should decide the format from
context, not treat the change as purely additive.

A v1 header carries none of the fields in §3, and all of them MUST be
null in a v1 header.

## 3. Header layout

164 bytes: the classic 80-byte prefix, then 84 more, in this order.

| Offset | Field | Width | Notes |
|---|---|---|---|
| 0 | `nVersion` | 4 | as serialized, bit 31 set — see §2 |
| 4 | `hashPrevBlock` | 32 | |
| 36 | `hashMerkleRoot` | 32 | |
| 68 | *time on wire* | 4 | see §3.1 |
| 72 | `nBits` | 4 | |
| 76 | `nNonce` | 4 | |
| 80 | `m_nonce2` | 4 | |
| 84 | `m_nonce3` | 4 | |
| 88 | `m_extranonce` | 16 | Stratum v1 extranonce |
| 104 | `m_time_offset` | 4 | see §3.1 |
| 108 | `m_txcount` | 2 | transaction count, see §5.2 |
| 110 | `m_flags` | 1 | see §3.2 |
| 111 | `m_xor_key_mask_clear_bits` | 1 | see §4.2 |
| 112 | `m_xor_key` | 16 | withheld from the pooling miner |
| 128 | `m_height` | 4 | signed; the block's own height, see §5.1 |
| 132 | `m_mm_rhs` | 32 | merge-mining commitment |

All integers little-endian, as elsewhere in Bitcoin serialization.

### 3.1 Time

The header carries the time **as adjusted**, and the wire carries it
adjusted back:

```
UseTimeOffset = 0x04              // bit 2 of m_flags

time_on_wire = (m_flags & UseTimeOffset) ? wrapping_sub(nTime, m_time_offset)
                                         : nTime
```

The subtraction wraps. An implementation that stores the wire value as
`nTime` is wrong whenever bit 2 is set, and the error is invisible until
the hash fails to match.

### 3.2 Flags

| Bits | Meaning |
|---|---|
| 0–1 | ASIC profile, 0–3 — selects a layout in §4.7 |
| 2 | `UseTimeOffset` |
| 3–7 | unused at time of writing |

## 4. The proof-of-work hash

Two primitives are involved, not one. Tagged hashes are BIP340-style
**SHA256**; only §4.6 and §4.7 use **BLAKE2b**. Calling the whole thing
"the BLAKE2b hash" is misleading.

`TaggedHash(tag)` is `SHA256(SHA256(tag) || SHA256(tag) || …)` as in
BIP340, so the tag contributes 0x40 bytes before any body.

For a v1 header the hash is SHA256d over the 80 bytes, unchanged.
Everything below is v2 only.

### 4.1 XOR key hash

```
xor_key_hash = SHA256(TaggedHash("Bitcoin block hash PoW XOR key") || m_xor_key)
```

Body is 0x10 bytes. A pooling miner is given this hash and never
`m_xor_key` itself, so it cannot compute the final hash until the block
is found.

### 4.2 XOR key mask

Zero when `m_xor_key` is null. Otherwise:

```
mask = SHA256(TaggedHash("Bitcoin block hash PoW XOR mask") || m_xor_key)
clear_bytes = m_xor_key_mask_clear_bits / 8
mask[0 .. clear_bytes]  = 0
mask[clear_bytes]      &= 0xff >> (m_xor_key_mask_clear_bits % 8)
```

The leading bits are cleared so the mask cannot affect the comparison
against the target — the work still has to be real.

### 4.3 Hidden previous block

```
prevblock_ordered_sane = reverse_bytes(hashPrevBlock)
prevblock_hidden       = SHA256(TaggedHash("Bitcoin prevblock header, hashed")
                                || prevblock_ordered_sane)
```

`hashPrevBlock` is stored in internal order; the "sane" ordering is its
reverse. Getting this backwards is wrong everywhere downstream.

### 4.4 `h1` — what the mining machine never sees

```
h1 = TaggedHash("Bitcoin block header 1")
        || version_as_serialized       (4)
        || prevblock_ordered_sane     (32)
        || m_height                    (4)
        || hashMerkleRoot             (32)
        || time_on_wire                (4)
        || 0x00                        (1)   reserved for extended 40-bit time
        || nBits                       (4)
        || uint32(m_txcount)           (4)   widened from 2 bytes
        || m_flags                     (1)
        || m_xor_key_mask_clear_bits   (1)
        || xor_key_hash              (32)   already a hash, from §4.1
```

Body is **119 bytes**; Knots asserts this and so should an
implementation.

Version, time and target are deliberately kept out of what the hardware
hashes, so an ASIC cannot be bricked by a future block version,
timestamp or difficulty.

### 4.5 `h2` — the merge-mining hook

```
h2      = TaggedHash("Merge-mining hook") || SHA256(h1) || zeros(16) || zeros(16) || m_mm_rhs
h2_hash = SHA256(h2)
```

Body is 0x60 bytes.

### 4.6 First BLAKE2b — the Stratum v1 payload

```
stream = uint32(0) || h2_hash || m_extranonce        // exactly 52 bytes
hash   = BLAKE2b(stream)                             // unkeyed, 32-byte output
```

The leading `uint32(0)` is the tail of Stratum's `coinb1`; its first
byte is implied by the hasher.

### 4.7 Second BLAKE2b — the ASIC profile

The layout branches on `m_flags & 3`. `zeros` is a 128-bit zero value.

| Profile | Stream |
|---|---|
| 0 | `prevblock_hidden` with its **first 6 bytes zeroed** ‖ `nNonce` ‖ `m_nonce2` ‖ `m_time_offset` ‖ `m_nonce3` ‖ `hash` |
| 1 | `nNonce` ‖ `m_nonce2` ‖ `m_nonce3` ‖ `m_time_offset` ‖ `hash` ‖ `h2_hash` |
| 2 | `zeros`×3 ‖ `h2_hash` ‖ `nNonce` ‖ `m_nonce2` ‖ `m_time_offset` ‖ `m_nonce3` ‖ `hash` |
| 3 | `zeros`×2, then exactly profile 2's stream |

Profile 1 orders the nonces differently *and* puts `h2_hash` last.
Profile 3 is not its own layout — it falls through to profile 2 in the
C++, giving five leading zero blocks in total.

```
hash = BLAKE2b(stream)
```

### 4.8 XOR and reverse

```
for i in 0 .. 32:
    block_hash[31 - i] = hash[i] ^ mask[i]
```

One loop applies the mask from §4.2 and reverses byte order at the same
time. `block_hash` is the block hash in **internal** order — the value
compared against the target.

Displayed forms are its reverse, as for every other hash in Bitcoin. So
the RPC's `hash`, and the `block_hash` in the test vectors, are
`hash[i] ^ mask[i]` written straight out with no reversal. An
implementation that compares its internal value against a displayed one
fails at the last step having got everything else right.

## 5. Consensus rules

### 5.1 Height

For a v2 header, `m_height` MUST equal the previous block's height plus
one. A chain client may therefore treat the header's height and the
index height as the same number.

### 5.2 Transaction count

`m_txcount` MUST equal the number of transactions in the block, and MUST
be zero in a v1 header. It is a header field distinct from any count a
node keeps for a block it has downloaded: a client following the chain
by headers first has `m_txcount` before it has the block.

Because it feeds `h1`, a client that cannot obtain it cannot compute the
hash.

### 5.3 Activation

Activation is by height, on `consensus.Blake2bHeight`:

- **At and above** it, headers MUST be v2. A v1 header is rejected with
  `bad-version-blake2b`.
- **Below** it, headers MUST be v1. A v2 header is rejected.

| Network | Height | Target shift |
|---|---|---|
| mainnet | 961640 | 22 |
| testnet4 | 150308 | 20 (default) |
| regtest | via `-testactivationheight=blake2b@N` | 20 (default) |

Heights are from branch `tmp`; earlier branches carry no activation
parameters at all.

### 5.4 The one-off target shift

The activation block's target is shifted left by `Blake2bTargetShift`,
clamped at the network's `powLimit`:

```
target = min(target << Blake2bTargetShift, powLimit)
```

2²² on mainnet is roughly a four-millionfold difficulty reduction. The
2016-block retarget is otherwise unchanged; there is no fast difficulty
adjustment.

The shift is applied inside `GetNextWorkRequired` and appears in the
header's `nBits`, so a client that reads difficulty from the header needs
no special case. One that re-derives expected difficulty across the
switch does, and rejects the activation block without it.

### 5.5 The proof-of-time headline

**The coinbase of the activation block MUST contain an agreed news
headline.** It is configured with `-blake2b_headline`, and a node
refuses to start without it. A block at the activation height whose
coinbase does not contain the string is rejected with `bad-headline`.

The value is chosen on the day, so it cannot be derived from the source.
An implementation that omits this rule cannot follow the chain past its
first v2 block.

## 6. RPC surface

`getblockheader` and `getblock` in verbose form report the header format
and, for a v2 header, the additional fields. Without them a client
reconstructs a header from named fields, computes SHA256d, and gets a
hash that disagrees with the `hash` the same call returned.

| Field | Present | Type | Notes |
|---|---|---|---|
| `header_version` | always | number | **2** for a v2 header, **0** for a v1 one |
| `txcount` | see notes | number | the block's count when the node has the block; the header's committed count when it has only the header; absent when it has neither |
| `nonce2`, `nonce3` | v2 | **hex string** | the `uint32` serialized little-endian, then hexed |
| `extranonce` | v2 | hex string | serialization order |
| `time_offset` | v2 | number | |
| `header_flags` | v2 | number | |
| `xor_key_mask_clear_bits` | v2 | number | |
| `xor_key` | v2 | hex string | serialization order |
| `mm_rhs` | v2 | hex string | serialization order |

Three things a client must not assume:

- **`header_version` is 0 for a v1 header, not 1**, and a node predating
  the field omits it altogether. Both mean v1.
- **`nonce2` and `nonce3` are strings**, not numbers.
- **The three byte-string fields are in serialization order**, unlike
  `merkleroot`, `previousblockhash` and the other hashes in the same
  result, which are reversed. §4.8's `block_hash` is reversed; these are
  not.

`version` remains the stored `nVersion` with the format flag masked off,
and `time` remains the adjusted time, not the wire time. The header's own
height is not reported separately because §5.1 makes it equal to
`height`.

## 7. The unified signature hash

Bitcoin has three signature messages: the original, BIP143 for segwit
v0, and BIP341 for taproot. The fork adds a fourth that replaces all of
them, and makes it **opt-in** so nothing already signed becomes invalid.

### 7.1 Opting in

`SIGHASH_UNIFIED = 0x20`, a bit in the hash type byte. A verifier
computes this message only when the bit is set; without it the script
type's existing message is used, unchanged.

Consensus reads the hash type from the last byte of the signature, so
the bit rides there and nowhere else. It cannot ride on
`SIGHASH_DEFAULT`, which appends no byte to hold it; an opted-in taproot
signature names `SIGHASH_ALL` instead, and the two mean the same thing.

For taproot and tapscript, a hash type outside
`{ALL, NONE, SINGLE} × ANYONECANPAY × UNIFIED` is rejected — BIP341's
strictness is kept, at consensus rather than by policy. Bare, P2SH and
segwit v0 keep the legacy reading, where the low bits select the output
type and anything else means `ALL`.

### 7.2 The message

Tagged with `TaggedHash("UnifiedSighash")`, laid out like BIP341's so
the two can be read side by side. `ss` is the tagged writer; the result
is its SHA256.

```
ss << u8(0)                            // epoch, as BIP341
ss << u8(nHashType)

ss << tx.version
ss << tx.nLockTime
ss << u8(0)                            // fifth locktime byte, reserved

if not ANYONECANPAY:
    ss << sha256(all prevouts)
    ss << sha256(all spent amounts)
    ss << sha256(all spent scriptPubKeys)
    ss << sha256(all sequences)

if output_type is neither NONE nor SINGLE:
    ss << sha256(all outputs)

ss << u8(script_type)                  // 0 bare, 1 witness v0, 2 taproot, 3 tapscript

if ANYONECANPAY:
    ss << this input's prevout
    ss << this input's spent output
    ss << this input's sequence
else:
    ss << u32(input index)

if not taproot:
    ss << scriptCode
else:
    ss << u8(annex present)
    if annex present: ss << annex hash

if output_type is SINGLE:
    ss << sha256(the output at this input's index)   // fails if absent

if tapscript:
    ss << tapleaf hash
    ss << u8(0)                        // key version
    ss << codeseparator position
```

### 7.3 What each part is for

**Spent amounts and scripts are committed to, for every input.** Legacy
does not commit to them, which is what makes CVE-2013-2292 and
CVE-2020-14199 possible: a signing device can be lied to about what it
is spending. Here the amount is signed whatever the script type.

**`script_type` domain-separates the script types**, so a signature made
for one is never valid for another. Knots does not default this byte
deliberately — a script version added later must be given its own value
rather than silently sharing the one for bare inputs, which would be the
cross-type collision the byte exists to prevent.

**The locktime is committed as five bytes**, not the four it occupies.
Four run out on 2106-02-07, and a later hardfork widening the field
would otherwise have to change this message and invalidate every
signature made under it. The fifth byte is zero until something sets it.

**Under `ANYONECANPAY` the input's position is deliberately not
committed to**, so the input can still be moved into another
transaction, which is the reason that flag exists.

**The annex is committed to** for taproot, or it would be malleable, and
the **tapleaf hash** for tapscript, or a signature for one leaf would be
valid for any other leaf under the same key.

### 7.4 Activation, and a trap

Consensus enables the message at the same height as the header change:
a block below it may not carry an opted-in signature, and from it
onwards may.

**Relay policy is not height-gated.** A node accepts an opted-in
signature into its mempool as soon as an activation height is
*scheduled*, on the reasoning that such a signature is the same
signature at every height, and that refusing it below the height would
only stop a lagging node from relaying what the chain it is catching up
to already accepts.

An implementation that produces signatures must key its own opt-in to
the **height**, not to the deployment being scheduled, or it will
produce transactions that its own chain cannot yet include. Knots
provides `-walletoldsigs` to force the legacy message.

### 7.5 Replay

The message is not chain-separated: nothing in it names BTK. It does not
have to be. BTC does not define `0x20`, so a chain without this rule
verifies an opted-in signature against its own message, and fails.

**A transaction whose signatures all opt in is therefore not replayable
onto BTC.** This is intended, not incidental — Knots tests it as
`unified_sighash_replay_protection`, asserting that the unified and
legacy messages differ for the same transaction, "which is what protects
against replay".

Two limits worth stating, because the property is easy to over-read:

- It protects **transactions**, not coins. A pre-fork UTXO spent this
  way remains spendable on BTC by a *different* transaction, signed the
  old way, by whoever else can sign for it. Splitting a coin still needs
  an input that exists on one chain only.
- It protects in **one direction**. A legacy-signed transaction is valid
  on both chains, as before.

### 7.6 What activation takes away

**A legacy signature whose hash type byte already sets `0x20` stops
verifying.** Before the fork the legacy algorithm reads such a byte —
`0x21`, say — by its low bits and treats it as `SIGHASH_ALL`; the extra
bit is ignored. From the activation height that same byte means the
signature opted in, so it is checked against the unified message
instead, and does not verify.

This is the only backwards incompatibility in the change. It matters to
anyone holding a pre-signed transaction, or a chain of them, whose hash
type carries that bit — a Lightning commitment transaction among them.
Knots covers it as
`unified_sighash_activation_invalidates_a_legacy_opt_in_byte`.

## 8. Test vectors

`src/test/data/block_header_v2.json` carries five vectors covering all
four ASIC profiles, with non-zero extranonce, XOR key and merge-mining
commitment, and a case using the time offset.

They expose **every intermediate**, not only the answer: `xor_key_hash`,
`h1`, `h2`, `blake2b_1`, `blake2b_2`, `mask`, `asic_input`, `serialized`
and `block_hash`. Assert against all of them — a construction this long
with four variants is not something to debug from one mismatched value
at the end.

In that file, `m_extranonce`, `m_xor_key`, `m_mm_rhs`, `hashPrevBlock`
and `hashMerkleRoot` are written byte-reversed, and so is `block_hash` —
see §4.8. **Note that this differs from the RPC**, which writes the three
byte-string fields in serialization order; converting between the two
requires reversing them. The intermediates `xor_key_hash`, `h1`,
`h2`, `blake2b_1`, `blake2b_2`, `mask` and `asic_input` are not: they are
raw byte strings in the order they are produced.

`h1` and `h2` in the file are the **hashes** of those tagged writers, not
the bodies described in §4.4 and §4.5.

## 9. Implementation notes

- Two primitives: tagged hashes are SHA256, only §4.6 and §4.7 are
  BLAKE2b. The signature hash of §7 is SHA256 throughout.
- Three byte-order reversals: §4.3, §4.8, and the blob fields in §6.
- The size assertions — 0x10, 119, 0x60, 52 — catch a mis-ordered or
  mis-sized field immediately, and are free.
- `time_on_wire` is conditional on a flag bit; using `nTime` directly is
  wrong whenever it is set.

## 10. Open questions

Design intent is not recoverable from code, and guessing at it is how a
description becomes misleading. These are left open deliberately.

1. **Why four ASIC profiles?** The layouts differ in field order and
   leading padding, which suggests accommodating existing hardware, but
   which hardware and why is not stated.
2. **Why is the mask cleared by a variable number of bits** rather than
   a fixed one? §4.2 says what happens, not what chooses the value.
3. **Why 2²² on mainnet** and 2²⁰ elsewhere? The figure is presumably a
   estimate of day-one hashrate; on what basis is not recorded.
4. **What is `m_mm_rhs` intended to commit to** in practice, and is any
   merge-mining scheme specified elsewhere?
5. **Is the reserved byte in §4.4 for 40-bit time** expected to be used,
   and on what timeline? The same question applies to the fifth locktime
   byte in §7.2.

6. **How many existing signatures does §7.6 invalidate in practice?**
   The rule is clear; the exposure is not. Anything pre-signed with a
   hash type byte carrying `0x20` stops verifying at activation, and
   whether that set is empty, small, or includes live Lightning channels
   is a question for people with wallet data rather than source.

Answers belong with the people who wrote the change.
